# 已上屏上下文与候选排序：能力验证

## 结论

可以从支持文档访问的宿主读取当前光标前的已上屏文字，并将其用于候选重排。应该以**当前按键对应的输入框和光标**为边界，不能把「同一个应用」或「上次上屏的文字」当作当前位置的上下文。

build 26 完成读取层的可行性验证；build 27 在其基础上增加保守的连续输入候选排序。原生 AppKit 和 WKWebView 的 19 个固定场景均匹配预期；这不是所有应用的正确率，也不是模型选词准确率。用户实际的 Codex 聊天编辑器仍需专门验收，不能用独立测试宿主替代。

## 「上」之后输入 hai

上下文是增加候选优先级的证据，不是强制替换规则：

| 光标前文 | 新拼音 | 期望倾向 |
| --- | --- | --- |
| 上 | hai | 提升「海」，形成「上海」；保留「还」供选择 |
| 我要去上 | hai | 更强地倾向「海」 |
| 墙上 | hai | 「还」可能更自然，不能只按最后一个「上」匹配 |
| 皇上 | hai | 需要完整语境，不能把所有「上 + hai」都拼成「上海」 |
| 空输入框，另一个输入框刚写过「上」 | hai | 使用当前输入框的普通候选，不能串用另一个框的「上」 |
| 原文已删除或光标移到句首 | hai | 不再沿用旧的「上」 |

工程现有 `Resources/pinyin_simp.dict.yaml` 中，`还 / hai` 的词频是 279642，`海 / hai` 是 12451；`上海 / shang hai` 是 46654，`上还 / shang hai` 是 393。它说明局部组合词频能为这个例子提供证据，但仅凭词表不能可靠处理「墙上还」等完整语义，因此不能据此宣布重排效果已经验证。

## 已实现的读取层

`Sources/SurroundingContext.swift` 是无历史缓存的局部读取器：

1. 从当前 IMK 客户端取选区与预编辑范围，使用文档的 UTF-16 坐标。
2. 普通光标取其左侧；选中文字时以选区起点为边界；有预编辑时以预编辑起点为边界，排除未上屏拼音和其他未提交文字。
3. 默认仅查询左侧 64 个 UTF-16 单元。宿主为避免截断代理对而扩大范围时，最多接受额外 2 个单元。
4. 优先使用能返回实际范围的 `string(from:actualRange:)`，验证范围、文本长度和光标锚点。仅在折叠光标下允许等长的属性文本查询兼容路径；选区情况下不把宿主退回的「选中文字」冒充前文。
5. 查询前后复核光标及预编辑范围。读取不到、范围矛盾或读取过程中发生移动时返回不可用，不拼接上次提交记录，不猜空白上下文。
6. 不依赖 `length()`。此前真实 Codex 日志曾出现文本非空但文档长度返回 0，故文档长度不能作为局部读取的必需条件。

依据是本机 Apple SDK 的 `IMKInputSession.h`，其中明确说明文档访问可能不受支持、查询可能退回选中文字、UTF-16 边界可能改变实际范围，以及完整文档长度查询可能昂贵。

## 实测结果

- `./scripts/context-test.sh`：24 项边界检查通过，覆盖长度为 0 / 不可用、未知光标、范围溢出、选区、同位置改字、读取中移动、无文档访问、长文、emoji 和预编辑排除。
- `./scripts/context-host-test.sh`：已安装 IMK 服务与独立宿主跨进程通信，19 / 19 场景与固定样本的前文哈希完全一致。
- 跨进程样本的读取耗时中位数 2.028 ms，最大值 3.760 ms。这只是本机这组样本的测量，不是所有宿主的延迟保证。
- 完整的精简范围和耗时数据见 [结构化结果](testing/context-capabilities-build26.json)。没有保存用户输入正文。
- 既有输入控制器的 40 项回归通过；测试后恢复了原输入偏好。常规版本的 Apple Silicon / Intel 构建通过，且确认二进制不含诊断通知名和启动参数。

| 实际宿主类型 | 已验证情况 |
| --- | --- |
| AppKit 文本框 | 「上」已上屏、较长语境、句中光标、选区替换、同应用换框后再返回、删除清空、多行 emoji、200 字以上内容的有界查询 |
| 真正的 Rime 预编辑 | 在固定宿主中调用输入会话生成未上屏拼音，通过实际 IMK 客户端读取，前文仍是「上」；不是把人工设置的 marked text 当作输入法生成的预编辑 |
| WKWebView 普通 input | 已有正文和光标；同位置切换到另一输入框 |
| WKWebView textarea | 已有正文、句中光标、选区 |
| WKWebView contenteditable | 已有正文、句中光标、选区、emoji 和 HTML 空白折叠 |

测试先等待真实 IMK 连接回复，再执行样本。刚重装后输入源已经可选但服务尚未完成启动，曾出现无回复；不把注册成功当成读取成功。

富文本中的 DOM 换行不一定是可见换行。本轮普通 HTML 将 `🙂第一行\n上` 呈现为 `🙂第一行 上`，IMK 返回的也是呈现后的空格。必须按编辑器的文档语义解读，不能拿 DOM `textContent` 强行判定输入法读错。

### 尚未完成的兼容性验收

在 Codex 内置浏览器里，自动化报告焦点位于本地测试页的 2 字输入框，IMK 仍返回同应用另一个会话的 43 单元光标位置。因此这次浏览器自动化样本属于**目标会话未对齐**，不计为 Codex 聊天框读取通过或读取失败。诊断只保存范围与哈希，没有把该会话正文写入日志或工具输出。

这再次说明，按应用标识寻找「当前会话」不够可靠。正式候选路径必须使用 `handle(event, client: sender)` 中本次按键携带的客户端；不能用异步全局通知选一个最近活跃的客户端来决定候选。

尚需覆盖真实 Codex 聊天编辑器、Chrome / Electron、常用聊天软件、跨窗口 / 分屏、富文本附件边界、撤销与重做、宿主异步更新，以及实际拼音连续输入。密码等不提供普通输入法会话的输入框不应启用这项能力。

## build 27：连续输入感知

设置 → 输入 → **连续输入时感知上下文**，默认开启，修改立即保存。关闭后恢复普通候选，不调用模型、不上传前文、不建立跨应用输入历史。

### 状态规则

| 操作 / 状态 | 结果 |
| --- | --- |
| 首次聚焦，包括已有正文的输入框 | 只建立读取得到的基线，不显示标记、不使用旧输入历史 |
| 本次聚焦中确认中文后继续输入 | 核对当前按键客户端、前文、预编辑范围和选区；通过后显示「上下文」 |
| 上 → 空格确认 → hai | 本地词库的「上海」组合证据可提升海，仍保留还等原候选 |
| 译英开启，确认的中文仍在草稿中 | 同样允许连续草稿上下文；空格不调用模型，也不提前上屏 |
| 连续输入标点、空格或确认混输英文 | 保持可核对的连续链；非中文结尾隔开词组关联，隐藏标记。再确认中文后可继续感知，无需重新聚焦 |
| 在候选中左右 / 上下移动 | 按显示顺序选词，保留手动高亮，不后台跳动 |
| 首项继续左移进入拼音、Shift 方向键、无候选时移动、Home / End | 本次焦点变脏，停止感知 |
| 删除、取消、Tab、粘贴 / 剪切 / 撤销等修饰键组合 | 本次焦点变脏，停止感知 |
| 鼠标点击、输入框身份变化、失焦、输入方式变化、进入编辑区 | 停止感知；宿主自动结束预编辑时保留此前可见的高亮词，不因退出感知换成别的字。临时编辑区首版不使用宿主上下文排序 |
| 同位置改字、宿主不能读前文、位置不匹配、异步插入尚未反映 | 停止感知，按普通候选继续输入 |
| 已变脏后继续打字 | 本次焦点不自动恢复；重新聚焦并重新确认中文才重新建立连续链 |
| 翻页 | 当段拼音使用普通顺序、隐藏标记；下一段仍须重新核对前文 |
| 关闭设置 | 立即隐藏标记并恢复原候选索引 |

「上下文」表示正在用可信前文评估候选，不表示每次都会改变首选。显示在方寸候选窗里；不向宿主正文插入提示字符。

AppKit 的 IMK 适配器可能将整个预编辑范围报告为选区：只在它精确等于本输入法生成的预编辑范围、且内部光标仍在末尾时接受这种表示。明确的光标操作仍会使状态变脏。宿主如果既不发送焦点 / 鼠标通知，也不暴露发生变化的范围，则无法保证检测到所有编辑；本功能只改变候选优先级，不自动替用户选词。

### 排序与边界

读取每次最多 64 个 UTF-16 单元。确认文本只用于核对预期的范围和前文，下一次按键仍须由宿主实际文本验证，不能把 `insertText` 调用成功当作已经显示成功。

从现有 `pinyin_simp.dict.yaml` 建立本地词频索引：仅考虑 2–8 字中文词、词频至少 100 的条目。在首页现有候选中，组合词频至少 1000 且为其他组合最高词频的 4 倍时，才将一个候选提升到首项。前文若以一个已知多字词结尾，会保留这个边界，例如「墙上」「皇上」不会只借用末尾的「上」拼成「上海」。这属于词组证据，不是语义理解，也不保证所有句子都选对。

候选与 Rime 原始索引保持映射，空格、数字键、鼠标、方向键都按屏幕上的候选提交。翻页及进入拼音编辑时返回普通顺序。全拼与双拼共用此逻辑；字词不在当前页、无强组合证据、夹杂英文、长句或局部已选拼音时，可能完全不改变候选。

最终 **27 / 27** 项跨进程检查匹配，包含原有 19 项读取场景，以及 AppKit / WebKit 各自的空框起点、确认「上」、`hai` 期间标记开启、最终得到「上海」。两个宿主的预编辑选区均实际返回 `[1, 3]`，验证了上述整段预编辑选区兼容逻辑。结果见 [build 27 验证记录](testing/context-continuity-build27.json)。这是受控输入流程验证，仍不是物理键盘或 Codex 聊天框的验收。

新增行为检查 76 项通过；读取边界 24 项、输入控制器 40 项、临时编辑区 129 项、核心输入 285 项、全拼与七种双拼翻页 344 项回归通过。

Rime 已有提交历史以及语言模型扩展入口，相关能力并非行业空白；本项目需要重点做好的是外部文本编辑后的真实上下文和输入位置校验。可参考 [Rime Context](https://github.com/rime/librime/blob/master/src/rime/context.h) 与 [Rime 扩展列表](https://github.com/rime/librime#plugins)，不能将现成提交历史等同于宿主当前正文。

## 如何复现诊断

正常构建不包含诊断监听器；上下文读取仅随输入事件进行，候选排序受上述设置与连续输入规则控制。

开发验证流程：

1. 运行 `FANGCUN_CONTEXT_PROBE=1 ./scripts/build.sh` 构建诊断版，并安装。
2. 停止旧的本项目输入法进程，再启动安装包并传入 `--context-probe /绝对路径/context-samples.jsonl`。测试脚本约定报告位置为仓库 `.build/context-samples.jsonl`。
3. 运行 `./scripts/context-host-test.sh`，查看 `.build/context-host-results.json`。必须检查各条的 MATCH / UNAVAILABLE / MISMATCH / SKIP，不能只看程序退出码。
4. 诊断完成后，用默认 `./scripts/build.sh` 重新构建并安装，移除诊断监听器。

`CONTEXT_PROBE` 条件编译的诊断仅在显式请求时读取一次局部上下文，保存范围、耗时及哈希；只有自有测试宿主可请求生成 / 清除固定拼音预编辑。它不向模型发送上下文，不使用剪贴板，也不合成全局键盘事件。
